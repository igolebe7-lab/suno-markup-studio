# План обновления Suno Markup Studio

Срез: 29.09.2026. Статус: **P0 реализован локально; выпуск на VPS проверяется отдельно. P1/P2 запланированы.** Основание: [исследование](research.md), [источники](sources.json), [машиночитаемые изменения](tags-update.json), [справочник](README.md).

## Цель и границы

Пользователь должен понимать, что он просит у Suno, куда вставлять каждый текст и почему результат может отличаться. Сохраняем плотный редактор, plain-text Lyrics, самостоятельную страницу справочника, авторские теги и облачное сохранение. Не добавляем собственную генерацию аудио, MIDI-редактор, управление чужим аккаунтом Suno или неподтверждённый API.

Подготовленные статьи объясняют весь существующий каталог; их полнота покрытия не равна доказанной работе каждого тега. Новые 12 записей проходят отдельное решение о публикации. Расширение не является обязательным условием выпуска полезной справки.

## Этап 1. Достоверные данные и справочник

**Файлы:** `apps/web/src/data/tags.ts`, `tagKnowledge.ts`, `domain/types.ts`; новые `data/knowledgeSources.ts`, `components/reference/ReferencePage.tsx`, `TagArticle.tsx`, `ReferenceNavigation.tsx`. Из `App.tsx` извлечь только соответствующий экран, без переписывания редактора.

1. Заменить общие описания тегов на `descriptionRu` из предложения; не менять существующие ID. ID с пробелами и регистром сохраняем.
2. Перед импортом статей выполнить редактуру: примеры, отмеченные `workflow-note`, не предлагать как текст для Suno. Не превращать 407 одинаково устроенных карточек в стену на одной странице.
3. Разделить `evidence` на доказательство конкретного утверждения и контекстную ссылку. Поля: `sourceId`, `scope`, `checkedAt`, `modelIds?`, `audioTested`. Показатель «работает на 95%» не вводить.
4. Существующие `TagConfidence` не менять резко в shared/custom DTO: добавить новую структуру доказательств справочника отдельно. Старое `official` скрыть или подписывать только там, где есть предметный источник.
5. Оставить TagSettingsPanel компактным. Одна ссылка «Подробнее о теге» ведёт к статье и сохраняет draft настроек. Не загружать туда длинные статьи.
6. Built-in: статья должна существовать для каждого `tag.id`. Custom: приватная статья собирается из описания пользователя, параметров и примеров; никаких выдуманных внешних подтверждений.

**Навигация:** самостоятельный экран. Слева/сверху список категорий и поиск, в центре одна статья, а не 407 развёрнутых статей. В статье: смысл, назначение, настройки, примеры, ограничения, источники, связанные теги. На узком экране список сменяется статьёй с явной кнопкой назад. Без нового дублирующего CategoryRail в редакторе.

**Адреса:** `#reference/tag/<encodeURIComponent(id)>`, `#reference/category/<category>`, `#reference/recipe/<id>`. Это эскиз контракта, Router не нужен. Поддержать `hashchange`, back/forward, перезагрузку на статье, неизвестный ID, сохранение строки поиска и позиции списка. Переход в справку не изменяет проект.

**Поиск:** точное совпадение ID/sunoText, затем название, aliases, русское объяснение, затем Fuse. «тихо» должно находить динамику и мягкую подачу; «chorus» должен различать припев и аудиоэффект. Alias не должен перекрывать отдельный точный тег. Статус источника и назначение служат фильтрами, не системой блокировки.

**Критерий готовности:** 407 действующих ID доступны из поиска; каждая статья имеет пример и описание реально отображаемых настроек; гипотеза визуально не выглядит как подтверждённый факт. В гостевом режиме справка полностью работает.

## Этап 2. Отдельные исключения и обратная совместимость

**Предлагаемые поля проекта:** `excludePrompt?: string` и `sunoContext?: { modelId?: string; mode?: 'custom' | 'simple' | 'studio' | 'sounds'; maxMode?: boolean; varietyNote?: string; notes?: string }`.

Это сохранённые сведения для ручного переноса, а не удалённые настройки Suno. `varietyNote` пока текстовое: не утверждаем неподтверждённый диапазон всех ползунков. Подтверждённое значение 0 можно объяснить в справке; UI-регулятор добавлять после проверки фактических границ и доступности на нужной модели.

**Хранение:** у Prisma Project уже есть `projectJson`. Для первой версии можно хранить дополнительные данные в нём, без новых таблиц и без DDL-миграции. Однако `toProjectDto()` сейчас перечисляет поля вручную: его необходимо обновить, иначе новые данные исчезнут при чтении. Необходимы изменения shared Zod DTO, create/patch схем, mapper, API merge-логики и store. Проверить сохранение необновляемых полей при PATCH старым клиентом.

Пределы объёма остаются защитными, не музыкальными: опираться на существующий общий request/body budget и щедрые `projectLimits`; для Exclude допустимо до 40 000 символов, заметок до 20 000 при проверке суммарного запроса. Не делать 260/1000 символов универсальным запретом Suno. Общий лимит тела, rate limits и авторизация не ослабляются.

**Переход:**

1. Старые JSON/localStorage/API-проекты без полей читаются с пустым Exclude и неопределённым контекстом. Не приписывать им модель v6 автоматически.
2. Кнопка «Перенести исключения» показывает найденные известные `avoid:`-элементы и результат до/после. Автоматически не разбирать неоднозначный свободный текст по запятым. Не трогать смысл песни и пользовательские формулировки.
3. Известные avoid-chips переводятся в Exclude только после подтверждения; убрать соответствующую часть Style без повторного добавления при следующем `buildStylePrompt`. Отмена и undo возвращают оба поля.
4. `project.version` уже увеличивается при изменениях; не использовать его как версию формата. Для внешнего формата при необходимости ввести самостоятельный `schemaVersion` с проверкой старого импорта.
5. Имена проекта и ID не меняются. Никаких массовых переписываний Supabase из скрипта деплоя.

**Экспорт:** `exportStyle` не добавляет исключения; новый `exportExclude` отдаёт чистую строку. Lyrics не содержит настроек аккаунта/модели. Пакет TXT/MD/DOCX имеет отдельные подписанные разделы Style, Lyrics, Exclude и необязательные заметки. JSON сохраняет новые поля. Старые кнопки копирования Style/Lyrics сохраняют смысл.

**Критерий:** исключение переживает reload, login/logout без потери draft, cloud round-trip, старый JSON-импорт и все форматы экспорта. PATCH названия старым клиентом не стирает Exclude.

## Этап 3. Корректная проверка проекта

**Файлы:** `domain/validation.ts`, `domain/lyrics.ts`, новые узкие pure helpers для разбора секций, unit-тесты. Не превращать парсер в строгий язык Suno: неизвестные инструкции разрешены.

1. Проверять последовательность скобок, а не только равенство количества: `][` и вложенность должны иметь понятную диагностику.
2. Разбирать теги отдельно от обычного текста: слово `trap` в строке песни не является жанровым тегом.
3. Конфликты анализировать в общей области Style/Exclude или в одной секции. Спокойный куплет и агрессивный припев допустимы. При неизвестной области выдавать «возможно противоречие», не категорический запрет.
4. Exclude `drums` против Style `live drums` отмечать как рекомендацию уточнить замысел. Локальное `no drums` в интро не запрещает барабаны в припеве.
5. Убрать требование Chorus Variation для разных припевов. Отсутствие припева/конца показывать по выбранной форме, как необязательное предложение.
6. Вместо предупреждения >260 символов дать счётчик; документированные лимиты, если будут найдены и проверены, хранить по модели/полю с источником и датой. Не обрезать ввод.
7. Неизвестный тег: «Нет статьи в нашем справочнике», а не «Suno его не поддерживает».

## Этап 4. Контекст v6 и полезные рецепты

**Контекст:** простая раскрываемая секция проекта, а не новая панель в header. Модель v6/v6-wild/v6-mini или «не указана», режим, заметки о настройках. Исторические модели показываются только для старых проектов как архивные. Никакого API-запроса от переключения модели.

**Рецепт правки:** выбрать секцию из outline, написать желаемое изменение и что сохранить. Детерминированный сборщик формирует отдельный запрос для Simple mode v6 или Studio Chat. Кнопка «Скопировать запрос», не «Применить в Suno». Выбранный текст песни передаётся только в буфер по явному действию.

**Рецепты:** [recipes.md](recipes.md) содержит поп-форму, контрастные припевы, инструментальную форму, дуэт и мягкий переход. Не превращать их в новые mandatory presets. Любая подстановка в непустой проект требует предпросмотра, подтверждения и undo.

**Не дублировать существующее:** уже есть дублирование проекта, undo/redo и пресеты. Для сравнения достаточно дополнить дубликат заметкой «что изменено» и необязательной ссылкой на результат Suno. Отдельную платформу A/B-тестирования не строить.

## Этап 5. Настройки и расширение каталога

- Схему предлагаемых изменений брать из `tags-update.json`, не импортировать файл вслепую: он не является текущим DTO Tag.
- Для end/stop убрать номер; для Instrumental убрать роль солиста; для динамики отделить артикуляцию, громкость и гармонию; для vocal разделить регистр и роль; для production разделить силу и область действия эффекта.
- Сохранять пользовательские значения старых custom tags. Переименование built-in ключа не должно молча ломать авторский тег. Предпочесть новые ключи с явным совместимым mapping.
- Не добавлять вторую сущность, если задача решается alias или существующим модификатором. У 12 кандидатов есть обоснование; отдельно решить, нужны ли самостоятельные описания микса или достаточно поиска по синонимам.
- Никаких magic tags из `doNotAddAsTags`. Не выводить `[Piano]` для тихой динамики по умолчанию, но не переписывать уже существующие Lyrics.

## План тестирования

### Данные и unit

1. Полное покрытие ID, валидные sourceId, не будущие даты, отсутствие дублирующихся IDs, корректные ссылки связанных статей.
2. Все показываемые настройки имеют объяснение. Снятые настройки не возникают в новых профилях, но старые custom-значения читаются.
3. Чистый экспорт каждого поля; `[Chorus]` не путать с chorus effect; Exclude не попадает в Style/Lyrics. TXT-кодировки и DOCX проверяются как раньше.
4. Миграция avoid: подтверждение/отмена/undo/неоднозначный текст/повторный запуск без дублей.
5. Валидация: `][`, `[Verse 12]`, свободный тег, разные припевы, инструментальная форма, межсекционный контраст, отрицание в Exclude, слово жанра в обычном стихе.

### API

Новые поля проходят Zod; mapper и PATCH сохраняют их; права владельца неизменны; старый клиент не стирает дополнительные данные; попытка сохранить огромную нагрузку ограничивается до записи в БД. Для DB-проверок использовать тестовую базу, не личные проекты Supabase.

### E2E

- Поиск по английскому тегу, русскому смыслу, псевдониму и параметру; категория + запрос вместе; нулевой результат.
- Статья по прямой ссылке, reload/back/forward, возврат в редактор без потери текста и pending DnD-настроек.
- Размеры 1440×900 и 390×844: нет коллизий, доступен поиск/назад/копирование; клавиатура и читаемый фокус.
- Custom tag другого пользователя не появляется в поиске справочника; logout убирает частные статьи.
- Exclude: ручной ввод, cloud save, reload, экспорт; отложенный/ошибочный ответ сервера не теряет локальную правку.
- Образцы не вставляются поверх проекта без подтверждения. В справке нет скрытых сетевых запросов к Suno.

Перед выпуском продуктовых изменений: `npm test`, `npm run build`, `npm run e2e`. Проверки документов выполняются отдельно, они не заменяют эти тесты.

## Ручная проверка результата в Suno

Это исследовательская процедура вне Suno Markup Studio, а не функция приложения: песни генерируются и прослушиваются в Suno. Наш редактор не воспроизводит аудио и не подключается к генерации. В этой поставке **нет ни одной аудиопроверенной записи**. Если позднее решим рекомендовать новые дескрипторы, для наиболее важных кандидатов можно провести ручную проверку:

1. Выбрать конкретную задачу, модель и один исходный текст. Записать все доступные настройки; не заявлять фиксированный seed, если он недоступен.
2. Вариант A без нового дескриптора, B с ним; остальных изменений нет. Например, измерять слышимость голоса, а не общее «качество».
3. При согласованном бюджете сделать хотя бы три независимые пары генераций. Это разведочный опыт, не статистическое доказательство надёжности.
4. Перемешать A/B при прослушивании, записать результат «да/частично/нет», побочные эффекты, модель, дату и ссылки. Для BPM и пауз измерять аудио, а не судить по названию трека.
5. Если заметного выигрыша нет или побочные эффекты велики, не продвигать кандидата в рекомендуемый каталог. Публичные отзывы оставлять отзывами.

## Выпуск и откат

1. Реализация ведётся в ветке `codex/sqlite-selfhost`; рабочий адрес размещён на собственном VPS по пути `/suno/`. Старые Render/Vercel не являются маршрутом выпуска этой ветки.
2. Новое поле проекта хранится в `projectJson` SQLite; DDL-миграция не нужна. Shared DTO, mapper и PATCH должны читать и сохранять его, в том числе когда старый клиент отправляет PATCH без нового поля.
3. Выполнить `npm test`, `npm run build`, `npm run e2e`. Затем зафиксировать изменения, отправить ветку в GitHub и дождаться Linux-артефакта CI.
4. Перед переключением только Suno-сервиса создать и проверить резервную копию SQLite. Не менять Caddy-маршруты Family Dashboard, WG, Amnezia, их сервисы, ключи и данные. Секреты не добавлять в документы и коммиты.
5. Развернуть новый Suno-релиз в отдельный каталог, переключить symlink `current`, перезапустить только `suno.service`; проверить вход, старый проект, изменение Exclude, обновление страницы, экспорт и три соседних сервиса.
6. При неуспехе вернуть предыдущий Suno-релиз. Откат API на версию без нового mapper может потерять Exclude при последующей записи: перед откатом прекратить запись или оставить совместимое чтение поля.
7. После выпуска сообщить SHA коммита, push, SHA релиза на VPS и результаты проверок. Локальное редактирование само по себе не обновляет VPS.

## Решения перед реализацией

Рекомендуется утвердить последовательность P0 → P1 → P2 и формат отдельного справочника. Никакое решение не требует сразу принимать все 12 новых дескрипторов. Перед добавлением реальных ползунков Suno отдельно проверить текущий интерфейс v6 и доступность на тарифах; до этого сохранять только заметки.
